# 四大模块 · 子能力全景（社区对标版）

> 定位：**能力设计地图**，不是合同承诺清单。口径以 SOW 为准的仍是 `00-功能点总索引.md`（AIP/AICS 60 项）。
> 本文件回答的是「按社区成熟实践，这四个模块**应该**有哪些子能力」，用于规划、评审与查漏。
> 生成：2026-10-08 ｜ 对标基线：2026 年社区与业界现状（含 Agentic Commerce 协议化、AEO/GEO、LLM 可观测合流）
> 关联纪律：`AI专项方案v2.docx` 1.5 建设范围边界 ｜ `knowledge/frontend/边界声明位的表达规范.md` ｜ ADR-014 纯云端+脱敏

## 〇、编号规则（先立规矩）

| 前缀 | 含义 | 可否对外承诺 |
|---|---|---|
| `AIP-xxx` / `AICS-xxx` | **SOW 合同功能点**，60 项，验收口径 | ✅ 可承诺 |
| `AIF-xxx` | 内部底座能力（非 SOW） | ❌ 内部 |
| **`CAP-X-nn`（本文件）** | **能力地图位**，规划与查漏用 | ❌ **严禁写进汇报承诺** |

> 为什么必须分开：上一轮刚清理过「坐席辅助不在清单却写成承诺」的事故。新增能力若沿用 AIP 编号，等于自己制造下一次口径污染。

**现状标记**：✅ 已入合同 ｜ 🟡 部分覆盖（有缺口）｜ ⬜ 社区标配但本项目缺失 ｜ 🔵 2026 新增维度

## 一、AI 商品中台（CAP-G）

现有 4 个子能力（商品库/类目/属性/智能体），智能体一项独占 8 点——**它是"流程环节"而非"能力域"，社区做法是按能力对象重切**。补全为 9 个子能力：

| 子能力 | 关键能力点 | 社区对标 | 现状 | AI 位判定（1.5） |
|---|---|---|---|---|
| CAP-G-01 商品库与源管理 | 多库纳管、源优先级、批次可重跑可对账、原始/治理分层 | MDM、dbt sources | ✅ AIP-001/002 | 规则/工程为主 |
| CAP-G-02 类目治理 | 类目树演进、批量挂载、四级对齐、错挂识别 | 电商类目预测（文本分类+层次化） | ✅ AIP-003/004 | 规则映射优先，语义兜底 |
| CAP-G-03 属性治理与抽取 | 属性模板生长、Schema 约束抽取、三路分层、合理性检测、品牌归一 | UIE/LLM 结构化抽取、JSON Schema 约束解码 | ✅ AIP-005/006/012/013 | 语义类，AI 主场 |
| CAP-G-04 商品内容智能 | 规范性校验、SEO 标题、审核结果反馈 | LLM 文案生成 + 规则校验 | ✅ AIP-008/009/011 | 生成类，AI 主场 |
| CAP-G-05 商品图像理解 | 以图搜图、主图质量分、图文一致性、白底/水印/违规标注、SKU 图与实物一致 | CLIP 类多模态表征、图像质检 | 🟡 仅违规检测（AIP-007） | 感知类，AI 主场 |
| CAP-G-06 商品知识资产 | 商品知识图谱、规格等效与替代料、场景/用途标签、参数问答对生成 | 电商 KG（属性-值-关系）、RAG 语料化 | 🟡 图谱在底座 d06，未成商品能力 | 语义类 |
| CAP-G-07 合规审核扩展 | 资质证照核验、广告法极限词、价格异常与虚标、禁限售目录、跨境合规 | 规则引擎 + OCR + LLM 语义判定 | 🟡 违禁词/图已覆盖 | **混合**：目录核验走规则 |
| CAP-G-08 SPU 与变体治理 | 跨源同款归一、变体（颜色/尺码/规格）识别、组合装拆分 | Entity resolution、blocking+matching | 🟡 同款已覆盖（AIP-010），变体弱 | ML 为主 |
| **CAP-G-09 AI 可读性治理（AEO/GEO）** | 机器可读商品 feed、结构化字段完整度评分、JSON-LD/Schema 标记、可验证事实锚定（价格/库存/售后承诺）、被 AI 引用的证据链 | 2026 社区新学科：从 SEO 转 AEO/GEO；UCP/ACP 商品数据契约 | 🔵 **完全缺失** | 规则+工程为主，语义补全用 AI |

**要点**：CAP-G-09 是 2026 的真实增量——搜索入口正在从"人搜商品"变成"AI Agent 替人选品"，商品数据若不可被机器可靠读取，会**直接被排除在候选集之外**。对 2B 采购商城同样成立（采购 Agent、集采目录对接）。这是"商品治理做好了"的**新验收标准**，不是营销概念。

## 二、AI 搜索中台（CAP-S）

现有 3 个子能力（搜索/导购/猜你喜欢）本质是**三个入口**，缺"检索技术栈"与"运营闭环"两条能力线。补全为 8 个：

| 子能力 | 关键能力点 | 社区对标 | 现状 | AI 位判定 |
|---|---|---|---|---|
| CAP-S-01 Query 理解 | 分词、纠错、补全、改写、意图识别、NER（品牌/型号/规格）、行业黑话与别名、多轮上下文 | Query understanding 全栈； synonym mining | ✅ AIP-015/016/017 + 意图 | 语义类，AI 主场 |
| CAP-S-02 召回与索引 | 倒排+向量混合、多路召回、召回融合、语义缓存、增量索引契约 | ES/OpenSearch + Milvus/Qdrant、hybrid retrieval、RRF | 🟡 底座有向量资产，召回策略未成能力 | ML/工程 |
| CAP-S-03 排序与重排 | 相关度、LTR、多目标（转化/毛利/合规）、多样性打散、同款聚合、业务规则插入 | LambdaMART/LightGBM、re-ranking | 🟡 多维排序（AIP-021），LTR/多目标弱 | ML 主场 |
| CAP-S-04 筛选与聚合 | 类目/品牌筛选、属性聚合、分面导航、结果计数 | Faceted search | ✅ AIP-018–020 | 规则/工程 |
| CAP-S-05 对话式导购 | 自然语言需求、多轮追问、个性化规则、历史会话、**约束硬过滤**、**推荐理由带证据** | RAG + tool-calling；2026 社区范式：价格/成分等约束进 SQL 硬过滤而非交给 LLM 解释，每条理由挂"看证据" | ✅ AIP-024–028 | 语义类 |
| **CAP-S-06 任务式采购** | 一句话生成整套采购清单（如"给某项目部配齐"）、BOM/清单批量匹配、缺项补全、预算约束求解 | 2026「从检索单品到解决整体需求」；Agentic 任务分解 | 🔵 **缺失**（2B 场景高价值） | AI 规划 + 规则校验 |
| **CAP-S-07 多模态搜索** | 拍照/截图找同款、**图纸与 BOM 表识别找料**、语音搜索、场景风格化搜索 | 视觉搜索、DocVQA、ASR | 🔵 演示页 b04 已提"图纸"但无能力点 | 感知类 |
| CAP-S-08 搜索运营与治理 | 零结果治理、badcase 闭环、热词/同义词挖掘、query 资产化、搜索可观测与告警 | Search analytics、query logging、OTel | 🟡 5.4 有机制描述，无产品化能力 | 分析产出（非 AI 功能点） |

**注意**：CAP-S-08 与商品侧的"选品/淘汰建议"同属**分析产出**，按 1.5 边界③归数据中台与报表，不立 AI 功能编号。

## 三、AI 客服中台（CAP-C）

合同给了 13 个二级模块、颗粒度最细，但**缺社区标配的"质检"与"工单"两条线**。按能力对象重切，补全为 11 个：

| 子能力 | 关键能力点 | 社区对标 | 现状 | AI 位判定 |
|---|---|---|---|---|
| CAP-C-01 接入与账号 | 多虚拟客服、排班、**多渠道统一（企微/钉钉/邮件/电话）** | Chatwoot（项目已在用）、Zendesk | ✅ AICS-001/002 🟡 多渠道 | 工程 |
| CAP-C-02 会话与消息 | 常驻面板/页面嵌入、多会话切换、引用商品订单、富媒体 | Live chat 标准能力 | ✅ AICS-003–007 | 工程 |
| CAP-C-03 人工接待与路由 | 排队、留言、转接、超时释放、**技能组路由、优先级与 SLA** | ACD/omnichannel routing | ✅ AICS-010–015 🟡 路由策略 | 规则 |
| CAP-C-04 智能体应答 | 意图识别、转人工硬规则、商品/订单/政策问询 | Intent + slot、RAG、function calling | ✅ AICS-016–019 | 语义类 |
| CAP-C-05 知识库运营 | FAQ 强制一致、分库专家智能体、引用规则、**知识自动挖掘、过期检测、冲突检测** | RAG 语料治理 | ✅ AICS-020–023 🟡 自动化弱 | 语义+规则 |
| **CAP-C-06 工单与售后协同** | 工单全生命周期、自动分类与分派、SLA 计时、跨系统流转、**售后与订单挂接** | Ticket lifecycle（Freshdesk/ZohoDesk） | 🔵 **合同仅有"售后申请"意图，无工单能力线** | ML 分类 + 规则分派 |
| **CAP-C-07 智能质检与合规** | 全量会话质检、服务红线检测、**不当承诺识别**、评分与申诉闭环 | QA/Review 是客服社区标配；LLM-as-Judge 全量替代抽检 | 🔵 **缺失**（风险内容监控 AICS-013 只是子集） | 规则前置 + AI 判定 |
| CAP-C-08 满意度与 VOC | 会话评价、情绪识别、流失/升级预警、投诉归因、趋势预测 | CSAT/NPS、sentiment、VOC analytics | 🟡 评价收集有（AICS-025），VOC 弱 | ML |
| CAP-C-09 坐席辅助 | 实时话术推荐、知识侧栏、自动小结 | Copilot 形态 | 🟡 **1.5 边界已声明：不在合同清单，远期** | 语义类 |
| CAP-C-10 运维与评测 | 模型可替换、效果评价、**对照评测门禁、回归红绿灯** | evals-as-CI（DeepEval/promptfoo 范式） | ✅ AICS-024/025 + AICS-030（内部） | 工程+评测 |
| CAP-C-11 语音客服 | ASR、TTS、语音工单、通话质检 | 全双工语音栈 | 🔵 缺失（远期） | 感知类 |

**CAP-C-06/07 是最该优先补的两条**：2B 采购场景里"售后无工单可追、服务质量无质检可查"是运营方被追问时最容易被击穿的点，且都属于社区标配而非前沿概念。

## 四、数据治理与 AI 数据中台（CAP-D）

**先澄清结构**：演示页里 `data-governance`（g01–g10 全挂 AIP 编号）是**商品中台的下钻视图**，不是第四域；真正的第四域是 `ai-data-platform`（6 域 8 节点）。合同侧无对应编号，PRD 侧仅 AIF-001~004（覆盖质量+评测，窄于演示页）。三套口径需以本表收敛。本节按社区数据中台全栈补全为 11 个子能力：

| 子能力 | 关键能力点 | 社区对标（2026） | 现状 | 备注 |
|---|---|---|---|---|
| CAP-D-01 数据集成与同步 | 电商 API/集采目录/行为日志接入、CDC、**schema 演进、幂等重跑、批次对账 fail-loud** | Kafka/Flink CDC、Airbyte | ✅ d01 + AIF 相关 | 已很扎实 |
| CAP-D-02 主数据与标准 | 类目树/字典/品牌/模板一处定义处处生效、实体解析、golden record | MDM | ✅ d02 | |
| **CAP-D-03 元数据与血缘** | 技术/业务元数据、字段级血缘、影响分析、资产目录 | **DataHub / OpenMetadata / Apache Atlas；OpenLineage 标准** | 🔵 **缺失**（底座最大空洞） | 无血缘则数据问题无法定位 |
| CAP-D-04 数据质量 | 规则断言、异常检测、质量 SLA、DQ 注册表、体检报告 | **Great Expectations / dbt tests / Soda** | ✅ d03 + AIF-001/002/003 | 已具社区水准 |
| **CAP-D-05 指标与语义层** | 指标定义唯一化、口径注册表、派生指标治理、**跨报表口径一致** | **dbt Semantic Layer / MetricFlow、LookML** | 🟡 有"口径三注册表"雏形，未成产品 | 直接治"数字打架" |
| CAP-D-06 AI 数据资产 | 向量资产、知识图谱、语料库、**特征平台（Feature Store）** | Milvus/Qdrant、**Feast/Tecton** | ✅ d05/d06 🟡 特征平台缺 | 注意：向量已"按需启用"，勿复活自建栈 |
| CAP-D-07 标注与数据回流 | 预标注+人工交叉复核、主动学习、bad case 闭环、标注质量验收 | **Label Studio**（方案已选）、argilla | ✅ d07 + 8.2 口径 | 口径已对齐社区共识 |
| CAP-D-08 模型与 Prompt 资产 | 多供应商网关、**prompt registry、版本与回滚、A/B 与灰度、模型资产台账** | **LiteLLM（ADR-014 已选）**、MLflow、prompt 版本化 | 🟡 网关有，prompt 资产化弱 | 纯云端路线下的核心控制点 |
| CAP-D-09 评测与门禁 | goldens 数据集治理、LLM-as-Judge、**OTel GenAI 语义约定 trace、评测进 CI、上线红绿灯** | **观测平台（Langfuse/Phoenix/Opik）+ CI 评测框架（DeepEval/promptfoo）组合**；Ragas 专 RAG | 🟡 主体已覆盖（AIF-004 + AICS-030）；**OTel trace 缺** | 社区定论：**分水岭是“有没有人持续维护 goldens”，不是选哪个工具** |
| CAP-D-10 安全与合规 | 脱敏网关、字段最小化、权限、**护栏（输入/输出）、审计、隐私合规** | **NeMo Guardrails / Llama Guard**、promptfoo red-team | ✅ d08 🟡 护栏未成能力 | C1 约束的落地件 |
| **CAP-D-11 成本与可观测（FinOps）** | **token 计量与归因、按业务域/功能点分摊、路由降级策略、预算告警** | Helicone/Portkey/LiteLLM 成本面板 | 🔵 **缺失** | **直接对应约束 C2「AI 按次收费」——目前只有原则没有度量** |

**CAP-D-11 是性价比最高的补齐项**：方案通篇强调"成本可控、分层调用"，但没有任何一处能回答"一次商品审核花多少钱、哪个功能点烧掉了预算"。没有这个仪表盘，C2 约束就是一句口号。

## 五、缺口汇总与优先级建议

四个大模块子能力合计 **39 个能力位**（商品 9 + 搜索 8 + 客服 11 + 底座 11）。脚本核数：**已入合同 14 处｜部分覆盖 17 处｜完全缺失 8 处**（G-09、S-06、S-07、C-06、C-07、C-11、D-03、D-11）。

| 优先级 | 缺口 | 为什么是它 |
|---|---|---|
| **P0** | CAP-D-11 成本与可观测 | 约束 C2 无度量手段，汇报必被追问 |
| **P0** | CAP-C-06 工单线 + CAP-C-07 质检 | 社区标配且 2B 运营刚需，缺失最易被击穿 |
| **P1** | CAP-D-03 元数据与血缘 | 数据出问题时无法定位上游，是"可持续运营"的地基 |
| **P1** | CAP-G-09 AI 可读性治理（AEO/GEO） | 2026 结构性变化，早做是差异化亮点，晚做是补课 |
| **P1** | CAP-D-09 补 OTel GenAI trace | 与 ADR-014 纯云端路线天然契合，降低未来换栈成本 |
| **P2** | CAP-S-06 任务式采购 | 2B 场景价值高但依赖 Agent 编排成熟度 |
| **P2** | CAP-S-07 多模态搜索（图纸/BOM） | 演示页已承诺"图纸"，能力位需补齐 |
| **P3** | CAP-C-11 语音、CAP-G-05 图像深化 | 远期演进 |

## 六、使用约束（避免这份地图反噬）

1. **对外材料只写 AIP/AICS**；CAP-* 仅用于内部规划与评审。
2. 每个 CAP 项进入承诺前，必须先过 **1.5 四条边界**（确定性判定不做 AI / 系统形态改造不做 AI / 经营分析不立 AI 功能 / 清单外不承诺），再走"补 SOW 功能点 → 立 PRD 卡"流程。
3. 底座类能力（CAP-D）**不重复建设**：检索栈、向量库自建均按现有"契约交付、按需启用"纪律，不复活已退役组件。
4. 本文件与 `商城AI需求追溯矩阵.md` 的关系：RTM 管"承诺了什么、谁实现"，本文件管"还应该有什么"。两者不互相覆盖。
