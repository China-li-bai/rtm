# 需求追溯矩阵（RTM）· 系统工程规范

> 建立：2026-09-26 ｜ 定位：V 模型双向追溯——每个业务场景能回答"由什么实现"，每个技术细节能回答"服务于什么"
> 参照：INCOSE 系统工程手册的需求管理实践（分解 decompose / 满足 satisfy / 实现 realize / 验证 verify 四类链接，双向完备）
> 事实源：[`model.yaml`](model.yaml)（唯一链接数据库）→ 由 [`gen_rtm.py`](../../../scripts/gen_rtm.py) 生成 [`../00-追溯矩阵.md`](../00-追溯矩阵.md)（生成物，禁手改）

## 一、追溯链五层模型

```
S（业务场景） ──decompose──▶ CAP（业务能力=AIP/AICS） ──satisfy──▶ COMP（技术组件=PRD卡） ──allocate──▶ TECH（技术锚点）
                                                                    │
                                                                    └──verify──▶ AC（验收用例）
```

| 层 | ID 规则 | 定义 | 数量 | 事实源 |
|---|---|---|---|---|
| S | S-01…S-n | 端到端业务场景（用户视角的一句话目标） | 10 | 本规范 §三 |
| CAP | AIP-xxx / AICS-xxx（合同编号即 ID，不自造） | 业务能力 | 60 | SOW 表 6/7 + 00-功能点总索引 |
| COMP | COMP-01…COMP-n | 技术组件 = 一张 PRD 卡 | 19 | 01-prd/ |
| TECH | 描述性锚点（真实表/端点/脚本名） | 技术细节锚点 | 每组件 2–5 | docs/STATUS.md / DATA_ASSET_MAP |
| AC | `<组件>-AC-n` | 验收用例（Given-When-Then） | 每组件 6–12 | PRD 卡 §9 |

## 二、双向完备规则（fail-loud 审计）

生成器对以下**全部**规则做机器校验，任一违反即 exit 1（阻断）：

1. **R1 分解完备（向下）**：每个 S 至少分解到 1 个 CAP
2. **R2 追溯完备（向上）**：每个 CAP 必须归属 ≥1 个 S——**无场景的能力不立项**
3. **R3 实现完备（向下）**：每个 CAP 至少由 1 个 COMP satisfy
4. **R4 来源完备（向上）**：每个 COMP 必须服务 ≥1 个 CAP——**无能力出口的组件是死代码**
5. **R5 锚定完备**：每个 COMP 至少 1 个 TECH 锚点（真实表/端点，禁空中楼阁）
6. **R6 验证完备**：每个 COMP 至少 1 条 AC——**无用例的能力不可验收**
7. **R7 编号守恒**：CAP 编号集合 == SOW 60 项全集（AIP-001–031 + AICS-001–029），多一个少一个都报错
8. **R8 双向一致**：CAP.comps 与 COMP.caps 互为镜像（生成器自动推导，手写不允许冲突）

## 四、变更影响分析

```bash
python3 scripts/gen_rtm.py --impact CAP-AIP-007    # 该能力变化影响哪些场景/组件/用例
python3 scripts/gen_rtm.py --impact COMP-06        # 该组件变化影响哪些能力/场景
python3 scripts/gen_rtm.py --audit                 # 仅跑八条完备性审计
```

影响传播规则：CAP 变更 → 向上（S）、向下（COMP → TECH → AC）双向列出。

## 五、与其他层的关系

- CAP 编号即 [00-功能点总索引](../00-功能点总索引.md) 的行 ID——索引管文档户口，本矩阵管追溯链
- COMP 即 `01-prd/` 的 PRD 卡——卡内 FR/AC 由生成器**直接从卡文件解析计数**（R6 的数字不是手抄的）
- TECH 锚点即 `docs/DATA_ASSET_MAP.md` / `STATUS.md` 的真实资产——只存名字指针，不复制口径
- Archi 模型（未来）：CAP/COMP 元素 ID 与本矩阵一致，模型导入后可出三层视图
