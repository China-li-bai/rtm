## 一、体系结构（四象限 + 一张地图）

大规模产品文档不写"一本总书"，而是**一张活地图 + 四类正文**。每个功能点按读者需求归入四象限：

| 象限 | 回答的问题 | 本仓位置 | 已有存量 |
|---|---|---|---|
| **地图（索引）** | 全部功能点在哪、状态如何 | `00-功能点总索引.md` | 本文档体系的入口，**先看它** |
| **PRD 卡（单一事实源）** | 这个功能点到底是什么、怎么验收 | `01-prd/{中台}/AIP-xxx-名称.md` | 8 张新卡 + 5 份存量收编 |
| **手册/FAQ/培训（How-to + Tutorial）** | 用户怎么用 | `02-手册/`（随 UAT 段建立，12/10 初版） | 待建，模板已备 |
| **参考 Reference** | 精确事实：指标、字段、架构 | 复用 `docs/` 根下已有文档，不搬家 | `EVALUATION.md` `ARCHITECTURE.md` `DATA_ASSET_MAP.md` `DECISIONS.md` |
| **原理 Explanation** | 为什么这样设计 | 复用 `docs/` 根下方案类文档 | `四大产品域功能模块梳理-*.md` `SMART_LISTING_PLAN.md` 等 |

**存量文档收编规则**：`docs/` 根下已有的产品文档（属性抽取、类目治理、客服场景等）不搬家、不重写，在 `00-功能点总索引.md` 挂链接并标注口径状态；待其下次大改版时再按 `templates/PRD模板.md` 收编为标准卡。

## 二、五条纪律（写进双周会）

1. **单一事实源（SSoT）**：每个功能点的定义、口径、验收只在 PRD 卡维护；用户手册、FAQ、培训材料、汇报 PPT 一律引用或摘编，**不得另写定义**。口径变更 = 改卡 + 卡内变更记录，衍生文档随之同步。
2. **先立卡后开发**：新功能点开工前必须先立 PRD 卡（社区标准结构：背景问题 / 用户故事 / 功能需求 FR 三节齐备），与《功能点施工清单》联动。需求写成**可验证的 FR 陈述**，不粘贴合同或外部文档原文；**Reference 类内容（指标、字段、架构）只链接不复制**（数字统一在 `00-功能点总索引.md` §参考层维护）。
3. **文档随节点发版**：每个里程碑（11/15 MVP、12/20 UAT、12/30 客服 MVP、1/15 试点）导出冻结版手册 + 发布说明，走 A 类交付流程；在线版继续活着。
4. **地图完整性优先于正文完整性**：索引表 60 项永远全量维护（无 PRD 的标 ⬜ 待写），正文跟着"有读者的功能"走，不追求一次补齐。
6. **追溯完备（系统工程 RTM）**：`architecture/model.yaml` 是场景→能力→组件→锚点→用例的链接数据库，由 `scripts/gen_rtm.py` 做八条完备性审计（fail-loud exit 1）并生成 [00-追溯矩阵](00-追溯矩阵.md)。新增功能点四步：model.yaml 加 CAP+COMP → 跑生成器 → 立 PRD 卡（卡内 FR/AC 被自动解析计数）→ 索引登记。
5. **结构与事实分层**：PRD 只写需求与设计（What/Why/How 设计层），实现进度以 `docs/STATUS.md` 为准（单一真源），卡内不维护进度数字；所有卡严格同构（结构即模板，支持未来组件化复用）。
